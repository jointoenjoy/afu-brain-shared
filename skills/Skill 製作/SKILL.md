# Skill 製作 · 心法

> 每次「要做一個新 Skill」「要改現有 Skill」時，先讀這份。
> 核心一句話：**Skill 是寫給未來的自己／agent 的 SOP，目的是讓它能「穩定觸發、穩定產出」。**

## 什麼時候才該做成 Skill
- 同一件事會做 **10 次以上** → 用 Skill 比每次貼 prompt 划算：一次設定、之後自動生效。
- 本質是「把工作流的記憶，從人腦轉到 agent 身上」。一次性的事不用做成 Skill。
- 不確定就先別做：先用 prompt 做幾次，等流程穩了、重複了，再沉澱成 Skill。

## 兩種做法
1. **訪談法（推薦新手）**：開個對話跟 Claude 說「幫我做一個技能包」，或用官方 `skill-creator`，它會進訪談模式一步步問你，幫你生出骨架。
2. **手寫法**：直接寫 `SKILL.md`。先寫一份**簡單**的，邊用邊長大——別一開始就追求完美結構，大部分 Skill 寫到第三版就夠用了。

## description 決定 80% 成敗（最重要）
Claude 只靠 `name` + `description` 判斷「這次要不要載入這個 Skill」。寫不好不是 Skill 壞了，是**根本沒被認出來**。

- 一定寫清楚兩件事：**「做什麼」** + **「什麼時候用」**。
  - ✗ 太空：「helpful writing Skill」
  - ✓ 夠具體：「產出對外提案簡報時，套用練息場品牌規範」
- 更高段：也寫清楚 **「不要用在哪裡」**，避免被誤觸發。
- 太籠統 → 不相關情境亂觸發；太狹窄 → 該用的時候沒載入。精準度直接決定觸發品質。

## 漸進式揭露（Progressive Disclosure）：分三層放資訊
context window 有限，所以 Skill 設計成「用多少、拿多少」：
- **Layer 1**：`name` + `description` —— 開新對話模型就看得到（決定要不要觸發）。
- **Layer 2**：`SKILL.md` 本文 —— 被觸發時才讀進來（放主要步驟與規則）。
- **Layer 3**：參考檔／附件 —— 真的用到才打開（放細節、範例、長文件）。

**關鍵推論**：真正重要、每次都要遵守的規則，要放在 Layer 1/2，**不要藏到 Layer 3**——藏太深 Claude 不一定每次讀得到。

## 三個常見陷阱（踩了 Skill 就不穩）
1. **過度集合（mega-Skill）**：把「品牌＋寫作＋研究＋翻譯＋簡報＋摘要」全包成一個。結果不是更強，是更難觸發、更難維護。→ **一個 Skill 做一件事**，拆開。
2. **把重點藏太深**：核心規則放到第二、三層參考檔。Claude 不一定每次完整讀到。→ 重要的往前放。
3. **給太多選項**：列一堆方法、一堆工具、一堆可選策略，反而讓 Claude 更不穩。→ **給一條最佳路徑**，少給選擇題。

## 維護（Skill 是活的，要定期照顧）
- **別寫死暫時性的東西**：寫死的工具版本、暫時規則、舊流程，時間久了會變成「穩定出錯」的來源。定期回來更新。
- **養「常見陷阱（Gotchas）」區塊**：Skill 裡訊號最強的內容就是 Gotchas。從「Claude 實際用這個 Skill 時踩過的失敗點」一條條累積上去——這是讓 Skill 越用越穩的關鍵。

## 做一個 Skill 的步驟（照這走）
1. 先確認值得做（重複 10 次以上嗎？）。
2. 寫好 `name` 和 `description`：講清楚做什麼、什麼時候用、不要用在哪。
3. 寫 `SKILL.md` 本文：一條最佳路徑的步驟，重要規則往前放。
4. 細節／長範例丟到 Layer 3 參考檔，本文只留必要的。
5. 一個 Skill 只做一件事，太雜就拆。
6. 加一個 **Gotchas** 區塊，之後遇到坑就回來補。
7. 在阿福大腦裡：放進 `skills/<名稱>/SKILL.md`，frontmatter 標 `status: 草稿`，commit + push；正式啟用前依規矩請大寶核可。
8. **同步名冊（別漏！）**：把新技能名字補進 `tools/dashboard/agents-roster.json` 對應類別（名字跟資料夾名一字不差），否則 aiflow 儀表板看不到它。開工 hook 會自動比對提醒，但養成「寫完 SKILL.md 立刻補名冊」的習慣最穩。

## Gotchas（用這個方法時自己踩過的坑，持續補）
